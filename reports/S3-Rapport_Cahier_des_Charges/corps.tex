\section{Fonctionnalités et Exigences du Système}
%===================================================================%

\subsection{Exigences Fonctionnelles}
% MoSCoW method (Must have, Should have, Could have, Won't have)

\begin{itemize}
    \item[$\bullet$] Must have :
    \begin{itemize}
        \item[$\circ$] La \glslink{page1_catalog}{page de catalogue} doit pouvoir afficher toutes les APIs actuellement mises à disposition des utilisateurs dans l'ordre alphabétique.
        \item[$\circ$] Le tri par défaut doit se faire par ordre alphabétique sur le nom des APIs.
        \item[$\circ$] Pour chaque API, la \glslink{page1_catalog}{page de catalogue} doit afficher son nom, sa version, sa révision, sa date de sa dernière mise à jour ainsi que son icône (ou un texte de remplacement si indisponible).
        \item[$\circ$] L'utilisateur doit pouvoir accéder à la \glslink{page2_api_doc}{page de documentation} d'une API en cliquant sur son nom dans le catalogue.
        \item[$\circ$] La \glslink{page2_api_doc}{page de documentation} doit afficher toutes les informations disponibles sur l'API telles qu'elles sont définies dans l'\glslink{apim}{API Manager}.
        \item[$\circ$] La \glslink{page2_api_doc}{page de documentation} doit offrir la possibilité à l'utilisateur de voir les \glslink{api_attachments}{documents et URLs supplémentaires} à la \glslink{api_doc}{documentation} de l'API.
        \item[$\circ$] Les "server URLs" présents dans la \glslink{api_doc}{documentation} de l'API doivent apparaître dans leur version correcte.
        \item[$\circ$] L'utilisateur doit pouvoir télécharger le \glslink{api_description}{fichier de description} d'une API depuis la \glslink{page2_api_doc}{page de documentation} de l'API, au format standard d'OpenAPI\footnote{\href{https://swagger.io/specification/v3/}{OpenAPI specification v3}} et avec les "server URLs" corrigés.
        \item[$\circ$] Les administrateurs doivent pouvoir consulter et supprimer les \glslink{api_data}{données} des APIs stockées dans le \glslink{storage}{répertoire de stockage des données} ainsi que pouvoir exclure des APIs.
        \item[$\circ$] Les administrateurs doivent pouvoir configurer les paramètres de l'application.
        \item[$\circ$] Le \glslink{api_data}{données} concernant les APIs doivent se mettrent à jour automatiquement à intervalle régulier.
        \item[$\circ$] Les administrateurs doivent pouvoir forcer la mise à jour des \glslink{api_data}{données} de toutes les APIs à tout moment.
        \item[$\circ$] Les administrateurs doivent pouvoir consulter les logs montrant les erreurs du programme, les connections des administrateurs ainsi que les modifications qu'ils ont effectués.
        \item[$\circ$] Les logs doivent être descriptifs et pouvoir montrer aux administrateurs l'origine de chaque message présent dans les logs (\glslink{back-end}{back-end}, \glslink{front-end}{front-end}, \glslink{scheduler}{scheduler}).
    \end{itemize}
    \item[$\bullet$] Should have : % <==> Nice to have
    \begin{itemize}
        \item[$\circ$] Le catalogue doit être muni d'une barre de recherche permettant d'explorer les APIs par nom.
        \item[$\circ$] Le catalogue doit être muni d'une liste de tags permettant de filtrer les APIs.
        \item[$\circ$] Le catalogue doit offrir la possibilité à l'utilisateur de trier les APIs par leur nom et leur date de dernière mise à jour.
    \end{itemize}
    \item[$\bullet$] Could have :
    \begin{itemize}
        \item[$\circ$] L'utilisateur doit pouvoir faire une demande d'accès à une API depuis la \glslink{page1_catalog}{page de catalogue} et/ou depuis la \glslink{page2_api_doc}{page de documentation} de l'API.
        \item[$\circ$] Les administrateurs doivent pouvoir faire remonter les statistiques d'utilisation de l'application via Matomo\footnote{\href{https://matomo.org/get/matomo_analytics/}{Matomo Analytics}}.
    \end{itemize}
\end{itemize}



\subsection{Exigences Techniques} % Technologies, formats, conventions, etc...
\begin{itemize}
    \item[$\bullet$] Les différentes parties de l'\glslink{application}{application} doivent être isolées dans des conteneurs docker :
    \begin{itemize}
        \item[$\circ$] le \glslink{back-end}{back-end} de l'application qui contient l'\glslink{extractor}{extracteur}, l'\glslink{importer}{importeur} et le \glslink{storage}{répertoire de stockage des données}.
        \item[$\circ$] le \glslink{front-end}{front-end} de l'application qui contient l'interface utilisateur.
        \item[$\circ$] le \glslink{scheduler}{scheduler} de l'application qui s'occupe de régénérer automatiquement le catalogue des APIs à intervalle régulier.
    \end{itemize}
    \item[$\bullet$] L'application doit être capable de se mettre à jour automatiquement à intervalle régulier sans aucune intervention.
    \item[$\bullet$] L'application doit stocker les fichiers de \glslink{api_description}{description} et de \glslink{api_doc}{documentation} des APIs sous format YAML.
    \item[$\bullet$] L'application doit stocker les variables d'environnement sous format texte.
    \item[$\bullet$] L'application doit suivre la licence open source MIT. % ou GPLv3
    \item[$\bullet$] L'application doit utiliser des technologies connues au SGSI.
    \begin{itemize}
        \item[$\circ$] L'application doit utiliser le framework Django pour l'\glslink{front-end}{interface web}.
        \item[$\circ$] L'application doit utiliser le langage Python pour la logique en \glslink{back-end}{back-end}.
        \item[$\circ$] L'application doit utiliser le scheduler cron pour la \glslink{scheduler}{planification automatique}.
    \end{itemize}
    \item[$\bullet$] L'application ne doit pas dépendre d'un service externe au SGSI.
    \item[$\bullet$] La \glslink{page1_catalog}{page de catalogue} de l'application doit suivre la même interface qu'\glslink{apim}{API Manager} :
    \begin{figure}[H]
        \centering
        \includegraphics[width=1.\textwidth]{img/mock-up_home.pdf}
    \end{figure}
\end{itemize}



\subsection{Exigences Non-Fonctionnelles}
\begin{itemize}
    \item[$\bullet$] L'application doit être très bien documentée tant au niveau de son architecture et organisation qu'au niveau du code et de son utilisation.
    \item[$\bullet$] L'application doit respecter la charte graphique de l'UCLouvain.
\end{itemize}

\section{Processus de Développement}
%===================================================================%
% Qu'est-ce qu'on veut de fonctionnel à montrer au client :
Le processus de développement se fera de manière itérative semaines par semaines tout au long du stage (méthode Agile). Chaque semaine, nous nous concentrerons sur un ensemble de fonctionnalités à implémenter afin de pouvoir présenter un prototype fonctionnel au client le vendredi.
