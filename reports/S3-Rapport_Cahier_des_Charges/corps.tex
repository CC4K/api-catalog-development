\section{Introduction}
%===================================================================%

\subsection{Objectifs et Public Cible}
Nous souhaitons créer un catalogue des \hyperref[api]{API}s disponibles pour les consultants externes au SGSI ainsi que pour les développeurs internes permettant de connaître leurs intérêts pour certaines APIs.

\subsection{Contraintes}
\begin{itemize}
    \item[$\bullet$] Le catalogue doit rester en lecture seule pour les utilisateurs finaux qui ne peuvent pas tester les APIs.
    \item[$\bullet$] L'application doit être documentée tant au niveau de son architecture et organisation qu'au niveau du code et de son utilisation.
    \item[$\bullet$] Ce projet se fera de manière itérative semaines par semaine tout au long du stage (méthode Agile).
\end{itemize}

\section{Fonctionnalités et Exigences du Système}
%===================================================================%

\subsection{Exigences Fonctionnelles}
% MoSCoW method (Must have, Should have, Could have, Won't have)

\begin{itemize}
    \item Must have : % "must have this", c'est-à-dire "doit être fait" (vital).
    \begin{itemize}
        \item La page de catalogue doit pouvoir afficher toutes les APIs actuellement mises à disposition des utilisateurs dans l'ordre alphabétique.
        \item Le tri par défaut doit se faire par ordre alphabétique sur le nom des APIs.
        \item Pour chaque API, la page de catalogue doit afficher son nom, sa version, sa révision, sa date de sa dernière mise à jour ainsi que son icône (ou un texte de remplacement si indisponible).
        \item Le catalogue doit être muni d'une barre de recherche permettant d'explorer les APIs par nom.
        \item L'utilisateur doit pouvoir accéder à la page de documentation d'une API en cliquant sur son nom dans le catalogue.
        \item La page de documentation doit afficher toutes les informations disponibles sur l'API telles qu'elles sont définies dans l'API Manager.
        \item La page de documentation doit offrir la possibilité à l'utilisateur de voir les documents et URLs supplémentaires à la documentation de l'API.
        \item Les "server URLs" présents dans la documentation de l'API doivent apparaître dans leur version correcte.
        \item L'utilisateur doit pouvoir télécharger le fichier de description d'une API aisément depuis la page de documentation de l'API.
        \item Le fichier de description téléchargé doit contenir tout les détails déjà présent sur la page de documentation de l'API.
        \item Le fichier de description téléchargé doit être au format standard de description d'API OpenAPI.
        \item Les administrateurs doivent pouvoir exclure des APIs.
        \item Les administrateurs doivent pouvoir consulter les données des APIs stockées dans le répertoire de stockage des données.
        \item Les administrateurs doivent pouvoir supprimer un répertoire d'API dans le répertoire de stockage des données.
        \item Les administrateurs doivent pouvoir configurer les paramètres de l'application.
        \item Le données concernant les APIs doivent se mettrent à jour automatiquement à intervalle régulier.
        \item Les administrateurs doivent pouvoir forcer la mise à jour des données d'une API.
        \item Les administrateurs doivent pouvoir consulter les logs montrant les erreurs du programme, les connections des administrateurs ainsi que les modifications qu'ils ont effectués.
        \item Les logs doivent être descriptifs et pouvoir montrer aux administrateurs l'origine de chaque message présent dans les logs (back-end, front-end, scheduler).
    \end{itemize}

    \item Should have : % "should have this if at all possible", c'est-à-dire devrait être fait dans la mesure du possible (essentiel).
    \begin{itemize}
        \item Le catalogue doit être muni d'une liste de tags permettant de filtrer les APIs.
        \item Le catalogue doit offrir la possibilité à l'utilisateur de trier les APIs par leur nom et leur date de dernière mise à jour.
    \end{itemize}

    \item Could have : % "could have this if it does not affect anything else", pourrait être fait dans la mesure où cela n'a pas d'impact sur les autres tâches (confort).
    \begin{itemize}
        \item Les administrateurs doivent pouvoir faire remonter les statistiques d'utilisation de l'application via Matomo.
    \end{itemize}

    \item Won't have : % "won't have this time but would like in the future", ne sera pas fait cette fois mais sera fait plus tard (luxe).
    \begin{itemize}
        \item L'utilisateur doit pouvoir faire une demande d'accès à une API depuis la page de catalogue et/ou depuis la page de documentation de l'API.
        \item La demande d'accès doit pouvoir être reçue par les administrateurs de la plateforme afin d'être traitée et acceptée/refusée.
    \end{itemize}
\end{itemize}

\section{Glossaire}\label{glossaire}
%===================================================================%
\begin{itemize}
    \item[$\bullet$] \textbf{API}\label{api} : Application Programming Interface ou Interface de Programmation d'Application est un ensemble normalisé de classes, de méthodes, de fonctions et de constantes qui sert de façade par laquelle un logiciel offre des services à d'autres logiciels.
    \item[$\bullet$] \textbf{API Manager}\label{apim} : Outil de gestion des APIs permettant de les créer, de les publier, de les sécuriser et de les surveiller.
    \item[$\bullet$] \textbf{API Controller}\label{apictl} : Outil en ligne de commande permettant de communiquer avec API Manager
    \item[$\bullet$] \textbf{Application}\label{FULL-APP} : l'application complète au sens général du terme, composée de 3 conteneurs docker : "back-end", "front-end" et "scheduler"
    \begin{itemize}
        \item[$\square$] \textbf{Back-end}\label{BACK-END} : le back-end de l'application qui contient l'extracteur, l'importeur et le répertoire de stockage des données
        \begin{itemize}
            \item[$\circ$] \textbf{Extracteur}\label{BACK-END:extractor} : l'extracteur de l'application qui s'occupe de récupérer les données des APIs depuis API Manager en utilisant l'API Controller, de les extraire de l'archive et de les passer à l'importeur
            \item[$\circ$] \textbf{Importeur}\label{BACK-END:importer} : l'importeur de l'application qui s'occupe de traiter et préparer les données pour le front-end et de les stocker dans le répertoire de stockage
            \item[$\circ$] \textbf{Répertoire de stockage des données}\label{BACK-END:storage} : le répertoire de stockage des données de l'application qui contient les données d'API traitées par l'importeur et prêtes à être utilisées par le front-end ainsi que toutes les données utiles pour faire fonctionner l'application
            \begin{itemize}
                \item[$\triangleright$] \textbf{Données d'API} : fichier de méta-données (api.yaml), fichier de documentation (swagger.yaml) et documents attachés (plain text)
                \item[$\triangleright$] \textbf{Configurations} : variables d'environnement, logs, blacklist, etc...
            \end{itemize}
        \end{itemize}
        \item[$\square$] \textbf{Front-end}\label{FRONT-END} : le front-end de l'application qui contient l'interface utilisateur
        \begin{itemize}
            \item[$\circ$] \textbf{Page de catalogue des APIs}\label{FRONT-END:page1_catalog} : la page de catalogue de l'application qui affiche la liste des APIs disponibles à l'utilisateur
            \item[$\circ$] \textbf{Page de documentation d'une API}\label{FRONT-END:page2_api_doc} : la page de documentation d'une API de l'application qui affiche les informations détaillées d'une API à l'utilisateur
        \end{itemize}
        \item[$\square$] \textbf{Scheduler}\label{SCHEDULER} : le scheduler de l'application qui s'occupe de régénérer automatiquement le catalogue des APIs à intervalle régulier
    \end{itemize}
\end{itemize}
